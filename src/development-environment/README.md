# C言語の開発環境

## 対応C規格

- **主要対象：** 全規格
- **学習内容：** 必要なツール、翻訳工程、警告、規格モード、デバッグ

## 学習目標

この章を完了すると、次のことができるようになります。

- エディタ、コンパイラ、リンカ、デバッガの役割を説明できる
- プリプロセス、コンパイル、アセンブル、リンクの各段階を確認できる
- 規格モードと警告を指定してプログラムをビルドできる
- コンパイルエラーとリンクエラーを区別できる
- デバッグ情報を付けてデバッガを起動できる

## 最小構成

C言語のプログラムを作って動かすために、まず必要なのは2つだけです。
ソースコードを書くための「エディタ」と、書いたコードをパソコンが実行できる形（実行ファイル）に変える「C処理系」です。
プログラムが大きくなってファイルが増えたり、バグ（間違い）の原因を調べたくなったりしたら、「ビルドツール」や「デバッガ」も使うようになります。

それぞれの道具の役割は次のとおりです。

1. **エディタ：** プログラムの文字（プレーンテキストのソースファイル）を書いたり直したりするノートのような道具です
2. **C処理系：** 人間の書いたC言語を機械語に変える道具一式（コンパイラ、アセンブラ、リンカ、標準ライブラリ）のことです
3. **デバッガ：** プログラムを途中で止めたり、変数の中身をのぞいたり、1行ずつ動かしたりしてバグを探す虫眼鏡のような道具です
4. **ビルドツール：** たくさんのファイルがあるときに、決められた手順でまとめてコンパイルしてくれる自動化ツールです

特定のエディタやビルドツールを必ず使わなければならないという決まりはありません。
学校やチームなど、すでに参加しているプロジェクトで決められた道具や手順がある場合は、そちらに合わせましょう。

## 処理系を確認する

GCC系やClang系といった代表的なC処理系が入っているか、どのバージョンかは、ターミナル（コマンドを打つ画面）で次のコマンドを実行して確認できます。

```bash
cc --version
cc -v
```

`cc --version`はバージョン番号を表示し、`cc -v`はさらに詳しい設定情報を表示します。
もし`cc`というコマンドが見つからない場合は、パソコンに入っている`gcc`や`clang`などのコマンド名で試してみてください。
インストール方法やパッケージの名前は、Windows、macOS、LinuxなどOSの種類によって異なるため、使っている環境の公式手順に従って準備します。

## 翻訳工程

人間が書いたC言語のソースコードは、そのままではパソコン（CPU）が理解できません。
実行ファイルができあがるまでには、大きく分けて「前処理」「翻訳（コンパイル）」「アセンブル」「リンク」という4つの段階を通ります。
普段は1つのコマンドで4つの段階を一気にやってくれますが、途中の結果を取り出して見ることもできます。
途中で何が起きているかを確認できると、エラーの原因を探すときにとても役立ちます。

### 前処理

前処理（プリプロセス）は、翻訳を始める前の「下ごしらえ」の段階です。

```bash
cc -E source.c -o source.i
```

`-E`オプションをつけると、前処理だけを行って結果を`source.i`に出力します。
ここでは、`#include`で別のファイルの中身を貼り付けたり、`#define`のマクロを置き換えたり、`#ifdef`などの条件に合わせて使う行を選んだりします。
「マクロが思った通りに展開されているかな？」と調べたいときに、`source.i`の中身を見ると確認できます。

### アセンブリコードの生成

次は、C言語のコードを「アセンブリコード」という、機械語にとても近い命令文へ翻訳する段階です。

```bash
cc -S source.c -o source.s
```

`-S`オプションは、リンクを行わずにアセンブリコード（`source.s`）だけを作ります。
コンパイラの最適化（プログラムを速く動かす工夫）によって命令がどう変わるか調べたいときは、最適化オプションもいっしょに指定して比べてみます。

### オブジェクトファイルの生成

アセンブリコードを、CPUが読める0と1の機械語のかたまり（部品）に変える段階をアセンブルといいます。
ここでできあがる部品ファイルを「オブジェクトファイル（`.o`）」と呼びます。

```bash
cc -c source.c -o source.o
```

`-c`オプションをつけると、リンクをせず、ソースファイル（翻訳単位）ごとにオブジェクトファイルを作ります。
大きなプログラムで複数のファイルに分かれているとき、変更したファイルだけを`.o`に作り直すために使います。

### リンク

最後の「リンク」は、できあがった複数のオブジェクトファイル（部品）と、標準ライブラリ（`printf`などの便利な機能のかたまり）を合体させて、1つの実行ファイルに仕上げる段階です。

```bash
cc main.o utility.o -o program
```

このコマンドでは、`main.o`と`utility.o`をつなぎ合わせて、`program`という実行ファイルを作っています。
もし「関数の宣言はあるのに、中身の定義がどこにも見つからない」場合や、「同じ名前の関数が2か所で定義されてぶつかっている」場合は、このリンクの段階でエラーが出ます。

## 警告と規格モード

コンパイラは、明らかな文法エラーだけでなく、「バグになりそうな怪しい書き方」を警告（ワーニング）として教えてくれます。
GCCやClangでは、次のように規格モードと警告オプションを指定してコンパイルするのがおすすめです。

```bash
cc -std=c17 -Wall -Wextra -Wpedantic source.c -o program
```

それぞれのオプションには次の意味があります。

- **`-std=c17`：** C17のルールを基準にして翻訳します
- **`-Wall`：** よくあるミスを見つける基本的な警告をまとめてオンにします（「すべての警告」という意味ではない点に注意しましょう）
- **`-Wextra`：** `-Wall`に含まれない追加の警告をオンにします
- **`-Wpedantic`：** 選んだC規格のルールから外れた書き方をしたときに、厳しく教えてくれます

警告が出たときに、いきなりオプションで警告を消すのではなく、「なぜ警告が出たのか」をコードを見て確認する習慣をつけましょう。
また、`-Werror`をつけると警告をすべてエラー扱いにしてビルドを止めることができます。
自動テスト（継続的インテグレーション）ではミスを見逃さないために便利ですが、コンパイラを新しくしたときに新しい警告が増えて急にビルドが止まることもあるので、使いどころを考えて選びます。

### 規格モードの例

使いたいC規格に合わせて、`-std=`の後ろを次のように変えられます。

```bash
cc -std=c90 -Wall -Wextra -Wpedantic source.c -o program
cc -std=c99 -Wall -Wextra -Wpedantic source.c -o program
cc -std=c11 -Wall -Wextra -Wpedantic source.c -o program
cc -std=c17 -Wall -Wextra -Wpedantic source.c -o program
cc -std=c23 -Wall -Wextra -Wpedantic source.c -o program
```

受け付けられるオプション名はコンパイラの種類やバージョンによって異なります。
C23への移行期のコンパイラでは、`-std=c23`ではなく`-std=c2x`を使う場合があります。

## 最適化とデバッグ情報

コンパイラには、プログラムを速くしたり小さくしたりする「最適化」の機能があります。
ただし、開発中にバグを調べているときは、動きが追いやすい設定にしておくのがコツです。

```bash
cc -std=c17 -Wall -Wextra -Wpedantic -g -Og source.c -o program
```

よく使うオプションは次のとおりです。

- **`-g`：** デバッガがソースコードの行番号や変数名を確認できるように、デバッグ情報（調査用の地図）を埋め込みます
- **`-O0`：** 最適化をほとんど行いません（書いた通りに素直に動きます）
- **`-Og`：** デバッグのしやすさを保ちながら、軽めの最適化を行います
- **`-O2`：** 本番用によく使われる、バランスのよい最適化を行います
- **`-O3`：** さらに積極的に速くしようとする最適化を行います
- **`-Os`：** 実行ファイルのサイズを小さく抑える最適化を行います

最適化のレベルを高くすると、コンパイラが不要な変数を消したり、処理の順番を入れ替えたりします。
そのため、デバッガで追いにくくなることがあります。
また、プログラムの速さを比べるときは、必ず同じ入力データと同じビルド条件（最適化オプションなど）で測りましょう。

## 実装の性質を確認する

C言語では、`int`型や`long`型がメモリを何バイト使うか、いくつからいくつまでの数を入れられるかが、パソコンやコンパイラ（処理系）によって変わることがあります。
次のプログラムを動かすと、自分の環境での型のサイズ（`sizeof`）と整数型の最小値・最大値を確認できます。

```c
#include <limits.h>
#include <stdio.h>

int main(void)
{
    printf("CHAR_BIT: %d\n", CHAR_BIT);
    printf("sizeof(char): %lu\n", (unsigned long)sizeof(char));
    printf("sizeof(short): %lu\n", (unsigned long)sizeof(short));
    printf("sizeof(int): %lu\n", (unsigned long)sizeof(int));
    printf("sizeof(long): %lu\n", (unsigned long)sizeof(long));
    printf("sizeof(void *): %lu\n", (unsigned long)sizeof(void *));
    printf("INT_MIN: %d\n", INT_MIN);
    printf("INT_MAX: %d\n", INT_MAX);
    printf("LONG_MIN: %ld\n", LONG_MIN);
    printf("LONG_MAX: %ld\n", LONG_MAX);
    return 0;
}
```

`<limits.h>`には、`INT_MIN`（`int`の最小値）や`INT_MAX`（`int`の最大値）などが定義されています。
`sizeof(char)`はC言語のルールで必ず`1`になりますが、1バイトが必ず8ビットとは限りません。
1バイトが何ビットなのかは、`CHAR_BIT`という定数で確かめられます。

### 規格版と処理系を確認する

今どのコンパイラを使っていて、どのC規格モードになっているかをプログラムの中から調べることもできます。
ただし、コンパイラ固有のマクロは、そのコンパイラでしか定義されません。
また、ClangはGCCと互換性のあるマクロ（`__GNUC__`）も定義するため、ClangのチェックをGCCより先に書くのがポイントです。

```c
#include <stdio.h>

int main(void)
{
#if defined(__clang__)
    printf("Clang: %d.%d.%d\n",
           __clang_major__, __clang_minor__, __clang_patchlevel__);
#elif defined(__GNUC__)
    printf("GCC: %d.%d.%d\n",
           __GNUC__, __GNUC_MINOR__, __GNUC_PATCHLEVEL__);
#elif defined(_MSC_VER)
    printf("MSVC: %d\n", _MSC_VER);
#else
    printf("Compiler: unknown\n");
#endif

#if defined(__STDC_VERSION__)
    printf("__STDC_VERSION__: %ld\n", __STDC_VERSION__);
#else
    printf("__STDC_VERSION__: not defined\n");
#endif

    return 0;
}
```

このように、処理系固有のマクロは「どのC規格か」ではなく「どのコンパイラの独自機能が使えるか」を判定するために使います。

## エラーを段階で分類する

エラーが出たときは、「どの段階で起きたエラーなのか」を見分けると、ぐっと早く直せるようになります。

### コンパイル時の診断

セミコロンのつけ忘れなどの文法ミス、型の間違い、宣言していない変数の使用などは、オブジェクトファイルを作る前のコンパイル段階で見つかります。
1つのミスが原因で、その下の行にも連鎖して大量のエラーが出ることがよくあります。
そのため、エラーメッセージは必ず「いちばん先頭のもの」から順番に確認して直しましょう。

### リンク時の診断

`undefined reference`（定義が見つからない）といったメッセージは、リンクの段階で起きます。
これは、必要な関数の中身が入っているオブジェクトファイルやライブラリをリンクし忘れたときや、関数名のつづりを間違えたときに発生します。
ヘッダーファイルに関数の宣言（プロトタイプ）を書き足すだけでは解決せず、その関数の本体（定義）をいっしょにリンクする必要があります。

### 実行時の問題

配列の範囲からはみ出して読み書きしてしまう（境界外アクセス）、すでに片付けたメモリを使ってしまう（解放済み領域の使用）、値を入れていない変数を使ってしまう（未初期化値の使用）といったミスは、コンパイルやリンクが成功しても、プログラムを実行したときにバグやクラッシュを引き起こします。

こうした見つけにくいバグを調べるときは、デバッガに加えて「サニタイザ」という監視ツールを使うととても効果的です。
サニタイザをオンにしてビルドすると、実行中に危ないメモリ操作が起きた瞬間にプログラムを止めて場所を教えてくれます。

```bash
cc -std=c17 -Wall -Wextra -Wpedantic -g \
  -fsanitize=address,undefined source.c -o program
```

`-fsanitize=address,undefined`は、メモリの不正アクセス（AddressSanitizer）と未定義動作（UndefinedBehaviorSanitizer）を見張る指定です。
なお、サニタイザはC言語の標準規格ではなくコンパイラの拡張機能なので、使える種類や対応環境は自分のコンパイラで確認しましょう。

## デバッガの基本操作

デバッガを使うと、プログラムを好きな行で一時停止させて、「今この変数に何が入っているか」を目で確かめられます。
代表的なデバッガであるGDBを使うときは、まず`-g`オプションでデバッグ情報を付けてビルドし、実行ファイルを指定して起動します。

```bash
cc -g -Og source.c -o program
gdb ./program
```

GDBの中でよく使う基本コマンドは次のとおりです。

```text
break main
run
next
step
print variable
continue
backtrace
quit
```

それぞれのコマンドの意味は次のようになります。

- **`break main`：** `main`関数の先頭で一時停止するように印（ブレークポイント）をつけます
- **`run`：** プログラムの実行を始めます
- **`next`：** 1行だけ進めます（関数呼び出しの中へは入らず、1ステップとして通過します）
- **`step`：** 1行だけ進めます（関数呼び出しがあれば、その関数の中へ入って追います）
- **`print variable`：** 変数`variable`の今の値を表示します
- **`continue`：** 次の停止位置か終了まで実行を再開します
- **`backtrace`：** どの関数からどの関数が呼ばれて今ここにいるか（呼び出し履歴）を表示します
- **`quit`：** デバッガを終了します

macOSなどでよく使われるLLDBなど、別のデバッガではコマンド名が少し異なります。

## Makefileの最小例

ソースファイルが増えてくると、毎回長い`cc`コマンドを手で打つのは大変ですし、打ち間違いも起きやすくなります。
そんなときは、`make`というビルドツールを使い、手順を`Makefile`というファイルに書いておきます。

`Makefile`には、「どのファイルを作るために、どのファイルが必要か（依存関係）」と「実行するコマンド（レシピ）」を書きます。
大切なルールとして、コマンドを書く行（レシピ行）の先頭は、スペースではなく必ずタブ文字（Tab）にします。

<!-- markdownlint-disable MD010 -->

```makefile
CC = cc
CFLAGS = -std=c17 -Wall -Wextra -Wpedantic -g

program: main.o utility.o
	$(CC) $(CFLAGS) -o $@ $^

main.o: main.c utility.h
	$(CC) $(CFLAGS) -c main.c

utility.o: utility.c utility.h
	$(CC) $(CFLAGS) -c utility.c

clean:
	rm -f main.o utility.o program
```

<!-- markdownlint-enable MD010 -->

この`Makefile`では、`make`と打つだけで必要なファイルだけが自動でコンパイルされ、`program`ができあがります。
`make clean`と打つと、作った`.o`ファイルや実行ファイルをきれいに片付けられます。
なお、`$@`は「作る目標ファイル名（ここでは`program`）」、`$^`は「材料になるファイル一覧（ここでは`main.o utility.o`）」を表す便利な記号です。

ビルドのコマンドを自分のパソコンのシェル設定（エイリアス）に隠しておくよりも、`Makefile`としてプロジェクトの中に残しておく方が、別のパソコンや他の人と同じ条件で確実にビルドを再現できます。
